0. 先看结论：这套工程到底在做什么

0.1 一句话概括

这是一套“电脑/手机 → 蓝牙串口 → STM32 → 四路电机驱动模块 → 四个麦轮”的遥控小车工程；STM32 不直接产生电机 PWM，而是把车体速度换算成四个轮子的目标速度，通过串口发送给驱动模块，由驱动模块完成底层电机闭环。

0.2 四个轮子的名字

本工程统一使用下面的名字，后面所有文档、命令和曲线都按这个顺序：

编号 名字 位置 常见用途
A 左前轮 车头左侧 wheel 0 对应 A
B 右前轮 车头右侧 wheel 1 对应 B
C 左后轮 车尾左侧 wheel 2 对应 C
D 右后轮 车尾右侧 wheel 3 对应 D

0.3 车体坐标的正方向

代码使用的坐标约定：

vx > 0：向前
vy > 0：向左
wz > 0：逆时针旋转（从上往下看，车头向左转）

这三个量分别是：

  • vx：前后平移速度，单位 m/s；
  • vy：左右平移速度，单位 m/s；
  • wz：旋转角速度，单位 rad/s。

注意：这是“数学约定”，不是“轮子实际一定这样转”。如果实车方向反了，先做单轮方向测试，再调整轮子符号或接线，不要直接猜。

1.3 电源和共地：这是最容易被忽略的安全问题

电源关系可以画成：

3S 电池
  ├─ 稳压模块 12V → 驱动模块功率电源
  ├─ 稳压模块 5V  → STM32 开发板
  └─ 稳压模块 3.3V → HC-04 蓝牙
       （也可以按实际模块，从 STM32 的 3V3 给 HC-04）

所有设备的 GND —— 必须连在一起 —— 共地

必须记住：

  1. GND 共地：STM32、驱动模块、HC-04、USB 转串口、稳压模块的 GND 要连在一起。没有共同参考地，串口字节会乱。
  2. 电压不能乱接：HC-04 的供电按模块要求使用 3.3V 或允许范围内电压；不要把 12V 直接接到 3.3V 逻辑设备。
  3. 驱动模块 UART 口的 5V 不要接到 STM32：只接 TX、RX、GND，避免倒灌。
  4. 第一次测试先架空轮子：让轮子离地，确认方向和计数，再放到地面。
  5. 开发板调试阶段优先用 ST-Link 供电：按你的要求，先只给开发板供电，确认程序正常，再接电机电源，降低烧板风险。
  6. 电池容量和放电倍率尚未最终确认：3S 电池能不能同时带动四个电机，要看容量、C 数和保护板；如果一加速就复位，优先怀疑电源跌落，而不是代码。

1.4 电源、逻辑电平和信号电平不是一回事

  • 电源：给设备提供能量，例如 12V、5V、3.3V；
  • 逻辑电平：芯片判断“0/1”的电压范围，STM32 是 3.3V 逻辑；
  • 信号：UART 的 TX/RX 上传输的字节波形。

一个设备“有 5V 电源”不代表它的 UART 信号可以安全接 3.3V 芯片。本工程按资料确认 HC-04 逻辑电平为 3.3V，驱动模块串口也按 3.3V 逻辑处理；接线前仍要核对模块丝印和资料。

3. 硬件原理：电机、编码器、PWM、H 桥、麦轮

3.1 直流减速电机

JGB37-520 可以理解为：

电机本体高速转动
  ↓ 减速箱（56:1）
输出轴低速、较大扭矩
  ↓
轮子转动

减速比 56 的意思是：电机内部转子转约 56 圈，输出轴才转 1 圈。它的好处是扭矩更大、速度更适合小车；代价是输出轴速度变慢。

3.2 编码器是什么

编码器把“转了多少”变成电脉冲。本工程使用 AB 相增量式霍尔编码器：

  • A 相：一路方波；
  • B 相：另一路方波；
  • A、B 有相位差，因此不仅能数脉冲，还能判断方向；
  • 电机转得越快，单位时间脉冲越多。

PPR、CPR 和 4 倍频

  • PPR（Pulses Per Revolution）：编码器每转的脉冲数。你的电机资料给的是 11 PPR。
  • 减速比：56。
  • 4 倍频：A、B 两相的上升沿和下降沿都可以计数，因此一个周期能数到 4 个边沿。

本工程当前使用的每输出轴转计数：

CPR = 11 PPR × 56 减速比 × 4 倍频
    = 2464 counts/rev

CFG_ENCODER_CPR = 2464.0f 就是按这个公式得到的。

【算法】这里的“4 倍频”不是魔法，而是利用 A/B 两相的 4 个边沿提高分辨率。实际计数会受模块内部解码方式、线序、干扰和轮子打滑影响，所以最终应以实测标定为准。

编码器方向

如果正转时计数增加，反转时计数减少，说明方向定义一致；如果相反，可能是：

  • A/B 相接反；
  • 电机 M+/M- 接反；
  • 代码中的符号需要取反；
  • 机械安装方向与坐标定义相反。

3.3 PWM 和 H 桥

PWM

PWM（Pulse Width Modulation，脉宽调制）是快速开关电源的技术。可以把它想成“很快地开灯、关灯”：

  • 开的时间比例叫占空比；
  • 占空比越大，电机平均电压越高，转速通常越快；
  • 频率要足够高，避免电机发出明显啸叫或抖动。

H 桥

H 桥由四个开关管组成，可以让电机：

  • 正转；
  • 反转；
  • 制动；
  • 停止。

AT8236 是单通道 H 桥驱动器，四路模块内部有四个通道，分别驱动四个电机。

本工程中 STM32 不直接生成 PWM。STM32 发送 $Car 目标速度，驱动模块内部完成 PWM 和速度闭环。这样做的优点是接线和代码简单，缺点是底层速度环参数由模块决定，STM32 不能直接调它的每个 PWM 细节。

3.4 麦轮为什么能全向移动

普通轮子只能前进/后退；麦轮（Mecanum wheel）的轮毂周围有一圈斜向辊轮，四个轮子以特定方向组合转动时，可以产生：

  • 前进/后退；
  • 左右横移；
  • 原地旋转；
  • 斜向移动。

本工程按以下布局理解：

A 左前       B 右前
C 左后       D 右后

按 车轮布局.jpg 的俯视图：A 轮辊轮向右上（/），B 轮向右下（\），C 轮向右下（\），D 轮向右上（/）。电机方向、编码器方向和代码符号仍要分别验证。这为横移和旋转提供了机械基础。

仍然需要做“单轮方向测试”，因为“辊轮方向正确”不等于“电机正负方向、编码器方向、代码符号”三者已经一致。

4. 通信：UART、蓝牙和协议

4.1 UART 是什么

UART（Universal Asynchronous Receiver/Transmitter，通用异步收发器）是一种常见的串口通信方式。双方约定：

  • 波特率：每秒传输多少位，例如 9600、115200；
  • 数据位：通常 8 位；
  • 校验位：通常无；
  • 停止位：通常 1 位。

本工程写成的 8N1 就是：

8 个数据位 + No parity（无校验）+ 1 个停止位

常见错误是“线接对了，但波特率不一致”，现象通常是：完全没数据，或者收到乱码。

4.2 三个串口的分工

STM32 串口 引脚 外设 当前波特率 用途
USART1 PA9/PA10 HC-04 蓝牙 9600 电脑/手机 ↔ STM32
USART2 PA2/PA3 四路驱动模块 115200 STM32 ↔ 驱动模块
USART3 PB10/PB11 USB 转串口 115200 有线调试/镜像观察

注意：config.h 里虽然有 CFG_DRIVER_BAUD 和 CFG_DEBUG_BAUD，但当前 usart.c 中 USART2/USART3 仍然是硬编码 115200；只有 USART1 引用了 CFG_BLUETOOTH_BAUD。这是一个已知的代码一致性点，不要误以为改宏就一定会改变所有串口。

4.3 经典蓝牙 SPP 与 BLE 的区别

  • 经典蓝牙 SPP（Serial Port Profile）：把蓝牙模拟成串口。Windows 配对后会出现“传入/传出”COM 口。本阶段使用它。
  • BLE（Bluetooth Low Energy）：低功耗蓝牙，通信模型不是传统串口，需要 GATT 服务/特征值。HC-04 虽然支持双模，但本阶段不依赖 BLE。
  • Windows 蓝牙设置中可能出现 COM7“传出”、COM8“传入”。不同软件的打开方式不同；如果连接成功但没有数据，首先核对上位机打开的是哪个口，以及驱动模块/固件是否真的在发数据。

4.4 二进制协议帧

本工程 PC ↔ STM32 的帧格式：

AA 55 LEN CMD DATA... CHECK
字段 长度 含义
AA 55 2 字节 帧头，告诉解析器“新帧开始”
LEN 1 字节 CMD + DATA 的总字节数
CMD 1 字节 指令码
DATA 0～N 字节 参数，按小端存放
CHECK 1 字节 (LEN + CMD + 所有 DATA) & 0xFF

为什么需要校验和

无线蓝牙可能受干扰，串口也可能丢字节。校验和不能纠正错误，但能发现“这一帧可能坏了”，避免把坏数据当成速度指令执行。

一个具体例子

发送“前进 1.0 m/s，vy=0，wz=0”：

vx = 1.000 m/s → ×1000 = 1000 = 0x03E8
小端存放：E8 03
vy = 0 → 00 00
wz = 0 → 00 00

CMD = 01
DATA = E8 03 00 00 00 00
LEN = 1 + 6 = 07
CHECK = (07 + 01 + E8 + 03 + 00 + 00 + 00 + 00) & FF = F3

完整帧：
AA 55 07 01 E8 03 00 00 00 00 F3

常见指令表

CMD 名称 数据 说明
0x01 手动速度 3 个 int16：vx、vy、wz，单位 0.001 进入手动模式
0x02 急刹停 无 直接发零速度，模式回空闲
0x04 位置 PID 停 int16 目标距离 mm 位置环走到目标附近
0x05 固定路线 route_id + 边长单位 当前固件 route.c 仍是占位实现
0x06 急停 无 立即清目标并停车
0x08 设置位置 PID Kp、Ki、Kd ×1000 在线改参数
0x09 编码器清零 无 记录当前计数为零点
0x0A 心跳 无 返回 ACK
0x0B 读参数 无 返回 0x85 参数帧
0x0C 设置限幅 最大线速度/角速度 ×1000 运行期限幅
0x0D 原地旋转 int16 角度，单位 0.1° 正数左转，负数右转

回报帧：

CMD 名称 内容
0x81 状态 模式、电压、四轮累计计数、四轮实际速度
0x82 曲线 四轮目标速度、四轮实际速度
0x83 ACK 心跳/指令确认
0x85 参数 当前 PID、限幅等

4.5 驱动模块文本协议

STM32 与四路驱动模块之间不是二进制帧，而是可读文本：

$Car:0.300,0.300,0.300,0.300!
$MOTOR_4CH_READ:encoder_20ms!
$MOTOR_4CH_READ:encoder_total!
$MOTOR_4CH_READ:battery!
$MOTOR_PARAM:8,11,56!

要点：

  • 每个命令以 $ 开头、以 ! 结尾；
  • $Car 的四个数范围通常是 -1.0～+1.0；
  • DriverComm_OnRxByte() 按 ! 切分一条响应；
  • 模块回包用 sscanf 解析成 DriverComm_Data_t 结构体；
  • 如果模块手册中的命令字、字段顺序或单位不同，必须以手册为准，不能只看代码猜。

4.6 帧解析状态机

接收端不能假设“一次串口中断就收到完整一帧”。可能一次只来一个字节，也可能一帧被拆成很多次中断。因此代码用状态机：

等待 AA → 等待 55 → 等待 LEN → 等待 CMD → 等待 DATA → 校验 → 交给控制层

这叫逐字节状态机。它的好处是：不需要知道数据什么时候到齐，来一个字节就推进一步。

5. 控制算法：从“会转”到“可控”

本章所有标题带 【算法】 的内容，都是可以通过测试工程和上位机调试中心单独观察、单独调参的部分。

5.1 控制周期与实时性

CFG_LOOP_MS = 20 表示控制主循环每 20ms 执行一次，也就是约 50Hz：

每 20ms：
  请求一次编码器 20ms 计数
  每 5 个周期请求一次累计计数（约 100ms）
  每 50 个周期请求一次电池电压（约 1s）
  根据当前模式计算一次输出
  每 100ms 上报一次状态/曲线

为什么需要固定周期？

  • PID 的积分和微分依赖时间；
  • 速度平滑按“每个周期的增量”计算；
  • 遥测曲线需要稳定的时间轴；
  • 主循环不能被长时间阻塞，否则控制会抖动。

5.2 开环与闭环

  • 开环：只发目标，不检查实际结果。例如只发 $Car:0.3,... 而不看编码器。
  • 闭环：测量实际值，和目标比较，再修正输出。

本工程有两层闭环概念：

外层：STM32 位置环（只用于 PID 精准停）
内层：驱动模块速度环（$Car 的目标速度 → 编码器 → PWM）

这也是为什么 0x07（速度环 PID）在当前固件中是预留：速度环在模块内部，STM32 不直接调它。

5.3 【算法】麦轮逆运动学

逆运动学的任务：

已知车体想怎么动（vx、vy、wz），求四个轮子各应该转多快。

代码中的公式：

A = vx - vy - (a + b) × wz
B = vx + vy + (a + b) × wz
C = vx + vy - (a + b) × wz
D = vx - vy + (a + b) × wz

其中：

a = 轴距 / 2（米）
b = 轮距 / 2（米）

本工程参数：

轴距 = 130 mm → a = 0.065 m
轮距 = 123.5 mm → b = 0.06175 m
a + b = 0.12675 m

为什么会有加减号？

  • 前进时四个轮子同向；
  • 横移时左右两侧的轮子需要不同组合；
  • 旋转时左侧和右侧轮子方向相反；
  • a+b 体现轮子离车体中心的几何距离，距离越大，同样的角速度需要更大的轮速。

这里的公式建立在特定的轮子编号、辊轮方向和坐标定义上。如果实车的 B/D 轮方向与代码假设相反，前进可能变成斜行，旋转可能方向错误。不要把公式当成“绝对真理”，要用单轮测试和整车测试验证。

5.4 【算法】归一化与最小驱动

驱动模块的 $Car 接受 -1.0～+1.0 的归一化速度。STM32 的轮速是 m/s，所以需要：

归一化轮速 = 轮子线速度 / CFG_MAX_WHEEL_SPEED_M_S

例如：

CFG_MAX_WHEEL_SPEED_M_S = 1.0 m/s
轮子目标 = 0.3 m/s
→ $Car 目标 = 0.3

然后代码会做最小驱动处理：

如果最大轮速的绝对值 < CFG_MIN_DRIVE：
    所有轮速按同一比例放大，使最大轮速达到 CFG_MIN_DRIVE

当前：

CFG_MIN_DRIVE = 0.30

原因是低占空比时电机可能克服不了静摩擦，出现“嗡嗡响但不转”或“转一下停一下”。但放大最小驱动也有副作用：

  • 起步更猛；
  • 低速微调变粗；
  • 如果地面摩擦变化，可能仍然抖动。

注意：这是“整体放大”，不是把每个轮子都强行设成 0.3；它保持四个轮子的比例关系，避免破坏运动方向。

5.5 缓起缓停已删除

2026-10-21 版本已删除普通手动、固定路线和旋转中的缓起/缓停及速度斜坡。

当前普通控制直接执行目标速度；需要平滑效果时，应在控制与测试页通过 PID 参数和机械标定获得稳定响应。

5.6 停止方式

方式 代码行为 现象 适用场景
急刹停 Motor_Stop() 发零速度，模式回 IDLE 立即停，可能有惯性冲击 紧急情况、测试
PID 位置停 位置环 + 编码器距离反馈 走到指定距离后停 控制与测试页

注意：本工程所说的“急刹”是让驱动模块目标速度归零，不是机械抱闸；轮子仍会因惯性滑行一小段。

5.7 【算法】原地旋转与时间标定

当前旋转不是角度闭环，而是时间控制：

旋转时间 = |目标角度| / 90° × CFG_ROTATE_MS_PER_90

当前：

CFG_ROTATE_MS_PER_90 = 900 ms
CFG_ROTATE_DRIVE = 0.60

例如发送 45°，代码会让轮子以固定速度转约 450ms。问题是：

  • 电池电压变化会改变实际转速；
  • 地面摩擦、轮子打滑会改变角度；
  • 负载变化会改变减速；
  • 所以 900ms 只是一个可调起点，必须实测标定。

标定流程：

  1. 在轮子悬空或低摩擦场地先确认方向；
  2. 发送 rot90 0.6 900；
  3. 用手机水平仪/量角器/地面标记测量实际角度；
  4. 若实际转了 80°，建议时间 = 900 × 90 / 80 ≈ 1013ms；
  5. 把建议值写回 CFG_ROTATE_MS_PER_90；
  6. 重新编译、烧录、复测 45° 和 90°。

5.8 【算法】PID 位置环

PID 是什么

PID 是 Proportional-Integral-Derivative 的缩写：

输出 = Kp × 误差
     + Ki × 误差积分
     + Kd × 误差变化率
  • P（比例）：误差越大，修正越猛；
  • I（积分）：长期存在的小误差会被累积，用来消除静差；
  • D（微分）：误差变化太快时给出阻尼，抑制超调。

本工程的位置环

目标不是“轮子速度”，而是“车体前进到某个位置”：

目标距离 = 起点距离 + 目标相对距离
当前距离 = 四轮编码器距离的平均值
误差 = 目标距离 - 当前距离
PID 输出 = 期望车体速度 vx

然后这个 vx 再经过麦轮逆运动学和 $Car 发给驱动模块。

当前 PID 代码的三个细节

  1. 积分项累加 error × dt；
  2. 积分做了限幅，防止积分饱和；
  3. 微分项当前是 Kd × (error - prev_error)，没有除以 dt。

这意味着：

  • Ki、Kd 的数值与 20ms 控制周期绑定；
  • 换控制周期后，同样的参数效果会变化；
  • 调参时不要盲目照搬别人的 Kp/Ki/Kd。

PID 调参顺序（位置环）

  1. 先令 Ki=0, Kd=0；
  2. 从小到大增加 Kp，直到能走到目标但略有超调；
  3. 如果总是差一点到不了，少量增加 Ki；
  4. 如果超调/来回摆，少量增加 Kd 或降低 Kp；
  5. 每次只改一个参数，记录现象；
  6. 用上位机“PID 调参”页和“PID 阶跃仿真”配合观察。

5.9 固定路线

当前固定路线由上位机执行，基本序列是：

前进 → 停顿 → 左转90° → 停顿
  ↑                         ↓
  └──── 重复 4 次（正方形）──┘

要点：

  • 路线是时间控制，不是每段都用编码器闭环；
  • 速度、边长、停顿时间都会影响实际轨迹；
  • 电池电压下降会让同样时间的行走距离变短；
  • 如果界面显示“到第三条边”但车还没走完，说明界面定时器/状态推进与实车运动不同步，需要检查路线状态机和定时器；
  • 固件 route.c 目前是空实现，0x05 不是当前 PC 路线的主路径。

USART2 收到字节 → DriverComm_OnRxByte()
USART3 收到字节 → Bluetooth_OnRxByte()

每个分支处理完后都要重新调用 HAL_UART_Receive_IT()，否则只会收到第一个字节。这是初学者最常见的串口问题之一。

control_mode.c 的 ControlMode_Poll()

这是整个控制系统的“心跳”：

时间到 20ms？
  → 请求编码器
  → 根据模式执行：
       IDLE：停车
       MANUAL：直接速度 + 逆运动学 + $Car
       BRAKE_SOFT：逐步减速
       POS_STOP：位置 PID
       ROTATE_ANGLE：定时旋转
       ROUTE：路线状态机
  → 每 100ms 发状态/曲线

chassis_control.c 的 Chassis_Inverse()

输入车体速度，输出四轮速度；这是麦轮“全向移动”的数学核心。必须配合正确的轮子编号、辊轮方向和符号。

bsp_encoder.c 的 Encoder_GetWheelSpeeds()

20ms 计数
  → 除以 CPR 得到圈数
  → 乘轮周长得到距离
  → 除以 0.02s 得到 m/s

driver_comm.c 的 DriverComm_OnRxByte()

按 ! 切分完整文本包，再用 sscanf 解析。它不主动理解“车体速度”，只负责把模块回包变成结构体字段。

bsp_bluetooth.c 的 Bluetooth_OnRxByte()

逐字节找帧头、读长度、读数据、校验，最后调用 ControlMode_OnCommand()。它不知道什么是“麦轮”，只负责把完整指令交给控制层。

6.6 代码注释怎么读

本工程的核心用户代码采用了“每行或每个关键语句配中文注释”的风格，例如：

float a = CFG_WHEELBASE_MM / 2000.0f;   /* 半轴距：前后轴距/2，换算成米 */

读注释时不要只看“这行做了什么”，还要问三个问题：

  1. 输入是什么？ 单位是什么？
  2. 输出是什么？ 送给谁？
  3. 如果这行错了，实车会有什么现象？

例如 CFG_WHEELBASE_MM 如果误写成 1300，a+b 会变大，旋转和横移时轮速差会明显不对，但直线前进可能看起来仍然正常。这就是“参数错误不一定会让车完全不转”的原因。

当前 CubeMX 自动生成的 HAL 文件保留了 ST 原始注释，不是每一行都有中文注释。后续如需严格满足“所有文件每行中文注释”，应在阶段 5 做一次专门的注释整理，而不是现在混在算法修改里。

8. 标定与实验流程

8.1 上电前的安全清单

  • [ ] 电池未接、开关关闭；
  • [ ] 所有 GND 共地；
  • [ ] 驱动模块 UART 的 5V 未接；
  • [ ] HC-04 供电电压正确；
  • [ ] 电机插头插紧；
  • [ ] 轮子架空；
  • [ ] ST-Link/串口线不会碰到电机电源；
  • [ ] 知道急停按钮/空格键在哪里。

8.2 实验 1：链路自检

  1. 开发板只由 ST-Link 供电；
  2. 打开上位机，选择 COM7，9600；
  3. 点“连接”；
  4. 观察是否有 RX 字节、状态帧、心跳 ACK；
  5. 若没有，先不要接电机电源。

判断标准：

  • 有 RX 字节：至少物理链路有数据；
  • 有 0x81 状态帧：STM32 在正常发遥测；
  • 心跳有 0x83 ACK：协议和固件都在工作；
  • 只有 TX 没有 RX：优先查蓝牙端口/波特率/接线。

8.3 实验 2：单轮方向和编码器

用测试工程或调试中心：

wheel 0 0.3   → A 轮
wheel 1 0.3   → B 轮
wheel 2 0.3   → C 轮
wheel 3 0.3   → D 轮

每次只转一个轮子，记录：

  • 轮子是否转；
  • 转向是否符合“前进正方向”；
  • 编码器计数是增加还是减少；
  • 是否有震动、停顿、异响。

如果某个轮子反向，先确认是机械安装方向还是代码符号；不要同时改所有轮子。

8.4 实验 3：编码器 CPR 标定

  1. 架空或低速；
  2. 发 enczero 清零；
  3. 让车走一段已知距离（例如直线 1000mm）；
  4. 记录四轮累计计数；
  5. 用测试命令 cpcal 1000 或上位机调试中心计算；
  6. 把建议 CPR 写回 CFG_ENCODER_CPR；
  7. 重新烧录并复测。

理论公式：

CPR = 计数 × 轮周长 / 实际距离

如果计算出的 CPR 与 2464 差很多，优先检查：

  • 实际轮径；
  • 减速比；
  • 编码器线数；
  • 4 倍频假设；
  • 轮子打滑；
  • 编码器线序/丢脉冲。

8.5 实验 4：最小驱动

从很小速度开始：

min 0.10
min 0.15
min 0.20
min 0.25
min 0.30

记录“开始连续转、不明显震动”的最小值。当前 CFG_MIN_DRIVE=0.30 是经验起点，不是永久真理。

8.6 实验 5：旋转标定

  1. 先确认左转/右转方向；
  2. 发 rot90 0.6 900；
  3. 量实际角度；
  4. 用 rotcal 实测角度 得到建议时间；
  5. 修改 CFG_ROTATE_MS_PER_90；
  6. 复测 45°、90°、连续旋转。

8.7 实验 6：PID 位置停

  1. 先用 pidstep 在电脑上做仿真，理解 Kp/Ki/Kd 的影响；
  2. 再在车上用低速度、短距离测试；
  3. 先 P，后 I，最后 D；
  4. 记录超调、到达时间、稳态误差；
  5. 位置环输出的是速度，最终仍由驱动模块速度环执行。

8.8 实验 7：固定路线

  1. 先把边长设小（如 400～600mm）；
  2. 速度设低（如 0.3～0.4）；
  3. 停顿设 500ms；
  4. 观察是否按“走一边→停→转→停”的顺序；
  5. 记录实际轨迹和界面进度是否一致；
  6. 如果界面跳步，先检查路线定时器和 route_gen，不要先改 PID。

9. 故障排查树

9.1 蓝牙连接成功但没有数据

按顺序查：

1. 上位机打开的是 COM7 还是 COM8？
2. 波特率是否 9600？
3. HC-04 的 TXD/RXD 是否交叉接到 STM32？
4. 是否共地？
5. KEY 是否悬空/没有进入 AT 模式？
6. STM32 是否真的在运行、是否烧了正确固件？
7. USART1 初始化是否 9600？
8. 用 COM5 有线调试是否能看到 0x81/0x82？

如果有线能看到数据、蓝牙看不到，问题更可能在蓝牙链路；如果两边都没有，问题更可能在固件/串口初始化。

9.2 电机不转

1. 驱动模块 12V 是否有电？
2. 电机插头是否插紧？
3. `$Car` 是否真的发出？
4. 速度是否低于最小驱动？
5. 驱动模块是否收到正确的电机类型/参数？
6. 是否处于 IDLE 或被急停覆盖？
7. 单轮 `wheel` 能否转？

9.3 轮子震动、转一下停一下

优先怀疑：

  • 速度太低，低于静摩擦/驱动阈值；
  • CFG_MIN_DRIVE 太小；
  • 电源电流不足或电压跌落；
  • 编码器丢脉冲，速度环误判；
  • 轮子机械卡滞；
  • 驱动模块参数/电机类型不匹配。

9.4 编码器为 0 或方向相反

  • 检查 A/B 相线；
  • 检查编码器供电和 GND；
  • 检查插头接触；
  • 单轮手动转，观察计数；
  • 若计数反向，确认是编码器 A/B 反接还是电机方向反接；
  • 不要把“编码器反向”和“电机反向”混为一谈。

9.5 前进斜行、横移方向不对、旋转方向不对

优先检查：

  1. 四个轮子的实际位置是否与 A/B/C/D 对应；
  2. 左右辊轮是否镜像；
  3. 单轮正方向是否一致；
  4. CFG_WHEELBASE_MM、CFG_TRACK_MM 是否量对；
  5. Chassis_Inverse() 的符号是否与实车布局匹配；
  6. 是否有某个轮子的 M+/M- 接反。

9.6 路线刚开始就跳到第三条边

优先检查：

  • 上位机路线定时器是否重复启动；
  • route_gen 是否让旧定时器失效；
  • 路线步骤是否在“发送指令”时立刻推进，而不是等动作完成；
  • 是否有多个窗口/多个定时器同时运行；
  • 蓝牙延迟是否让状态反馈滞后。

9.7 PID 抖动或超调

  • Kp 太大：响应快但容易超调/振荡；
  • Ki 太大：消静差但容易积分饱和；
  • Kd 太大：对编码器噪声敏感；
  • 控制周期不稳定：PID 的 dt 不准；
  • 机械间隙/打滑：编码器看到“到了”，车体未必真的到了。

9.8 Keil 编译/烧录问题

参见 Keil使用导航.md。最常见的三类：

  1. 编译器版本不对（AC5/AC6）；
  2. 头文件路径没加；
  3. ST-Link/Flash 算法没配置好。
